## Summary

Convex is a reactive TypeScript-native backend-as-a-service that replaces Supabase entirely: it provides the database, server functions (queries/mutations/actions), and real-time reactivity in one package. Unlike Supabase's PostgreSQL + REST/RLS model, Convex runs TypeScript functions directly in the database layer, auto-generates fully typed client APIs from your schema, and pushes live updates to `useQuery` subscribers automatically — no manual subscriptions, no polling.

The auth migration to Convex requires a custom JWT-based approach because this app uses wallet signing (not OAuth). The proven pattern — confirmed via the official Convex stack.convex.dev NextAuth adapter guide — is: Next.js server API route signs a short-lived JWT with an RSA private key after verifying the wallet signature → JWT is stored client-side → a `useAuth` hook passes the JWT to `ConvexProviderWithAuth` → Convex verifies via the JWKS public key endpoint. This keeps the wallet signature verification on the Next.js server (where `nacl`/`tweetnacl` already works) and delegates identity to Convex.

The sync operation (Helius fetch + trade parsing + DB write) should be a **Convex action** calling internal mutations. This is the correct Convex pattern for external API calls that then write to the DB. The current Next.js API route for `/api/trades/refresh` can be replaced by a Convex action + HTTP action or kept thin as a proxy. Reactivity is automatic once data is in Convex — the dashboard's `useQuery` hooks update instantly without any websocket management.

**Primary recommendation:** Use `customJwt` Convex auth with RSA key pair (jose library), keep wallet signature verification in a Next.js API route, migrate all DB operations to Convex mutations/queries, and move the sync logic to a Convex action that calls `internalMutation` to write trades.

### Pattern 1: Schema Definition
**What:** All tables defined in `convex/schema.ts` using `defineSchema` and `defineTable`.
**When to use:** Once, as the foundation. All generated types flow from this.

```typescript
// convex/schema.ts
// Source: https://docs.convex.dev/database/schemas
import { defineSchema, defineTable } from "convex/server";
import { v } from "convex/values";

export default defineSchema({
  wallets: defineTable({
    userId: v.string(),              // Convex tokenIdentifier (from JWT sub)
    walletType: v.union(v.literal("trading"), v.literal("vault")),
    address: v.string(),
    balanceSol: v.number(),
    balanceUsd: v.number(),
    currentTier: v.optional(v.number()),
    lastSyncedAt: v.optional(v.string()),
  })
    .index("by_user", ["userId"])
    .index("by_address", ["address"])
    .index("by_user_type", ["userId", "walletType"]),

  trades: defineTable({
    userId: v.string(),
    tradingWalletId: v.id("wallets"),
    tokenMint: v.string(),
    tokenSymbol: v.optional(v.string()),
    totalEntrySol: v.number(),
    totalExitSol: v.number(),
    netProfitSol: v.number(),
    roiPercent: v.number(),
    totalFeesSol: v.number(),
    netProfitUsd: v.optional(v.number()),
    roiMultiplier: v.optional(v.number()),
    tierAtTrade: v.number(),
    losingStreakAtTrade: v.number(),
    baseCashoutPercent: v.number(),
    roiBonusPercent: v.number(),
    streakMultiplier: v.number(),
    goalBoostMultiplier: v.number(),
    finalCashoutPercent: v.number(),
    recommendedCashoutSol: v.number(),
    status: v.union(v.literal("pending"), v.literal("confirmed"), v.literal("overridden")),
    actualCashoutSol: v.optional(v.number()),
    positionOpenedAt: v.optional(v.string()),
    positionClosedAt: v.string(),
  })
    .index("by_user", ["userId"])
    .index("by_user_token", ["userId", "tokenMint"])
    .index("by_wallet", ["tradingWalletId"]),

  userState: defineTable({
    userId: v.string(),
    currentLosingStreak: v.number(),
    lastTradeAt: v.optional(v.string()),
  })
    .index("by_user", ["userId"]),

  goalSettings: defineTable({
    userId: v.string(),
    monthlyGoalUsd: v.number(),
    currentMonthProgressUsd: v.number(),
    currentMonth: v.string(),
    boostActive: v.boolean(),
    boostPercent: v.number(),
    boostActivatedAt: v.optional(v.string()),
    boostExpiresAt: v.optional(v.string()),
    lastSundayCheck: v.optional(v.string()),
  })
    .index("by_user", ["userId"]),
});
```

**Key naming decision:** Use camelCase field names in Convex schema (idiomatic for Convex/TypeScript) rather than snake_case (Supabase convention). This eliminates the type mismatch that caused the `as any` casts — generated types will exactly match field names used in code.

### Pattern 2: Custom JWT Auth (Wallet-Based)
**What:** RSA-signed JWT issued by the Next.js server after wallet signature verification. Convex verifies the JWT via JWKS endpoint.
**When to use:** This is the auth pattern for the entire migration.

**Step 1 — Generate RSA keys (one-time script):**
```javascript
// scripts/generate-keys.mjs
// Source: https://stack.convex.dev/nextauth-adapter (adapted pattern)
import { generateKeyPair, exportPKCS8, exportJWK } from "jose";

const { privateKey, publicKey } = await generateKeyPair("RS256");
const privateKeyPem = await exportPKCS8(privateKey);
const publicKeyJwk = await exportJWK(publicKey);

const jwks = JSON.stringify({ keys: [{ ...publicKeyJwk, use: "sig", kid: "pisp-key-1" }] });

console.log("JWT_PRIVATE_KEY=", JSON.stringify(privateKeyPem));
console.log("JWKS=", jwks);
```

**Step 2 — Convex auth config:**
```typescript
// convex/auth.config.ts
// Source: https://docs.convex.dev/auth/advanced/custom-jwt
import { type AuthConfig } from "convex/server";

export default {
  providers: [
    {
      type: "customJwt",
      applicationID: "profit-is-profit",
      issuer: process.env.CONVEX_SITE_URL!,  // your .convex.site URL
      jwks: process.env.CONVEX_SITE_URL + "/.well-known/jwks.json",
      algorithm: "RS256",
    },
  ],
} satisfies AuthConfig;
```

**Step 3 — JWKS HTTP endpoint (Convex serves public key):**
```typescript
// convex/http.ts
// Source: https://stack.convex.dev/nextauth-adapter (adapted)
import { httpRouter } from "convex/server";
import { httpAction } from "./_generated/server";

const http = httpRouter();

http.route({
  path: "/.well-known/jwks.json",
  method: "GET",
  handler: httpAction(async () => {
    return new Response(process.env.JWKS, {
      status: 200,
      headers: {
        "Content-Type": "application/json",
        "Cache-Control": "public, max-age=15",
      },
    });
  }),
});

export default http;
```

**Step 4 — Next.js auth/verify route signs JWT after signature check:**
```typescript
// src/app/api/auth/verify/route.ts (updated)
// Source: adapted from https://stack.convex.dev/nextauth-adapter
import { SignJWT, importPKCS8 } from "jose";
import nacl from "tweetnacl";
import bs58 from "bs58";

export async function POST(request: NextRequest) {
  const { publicKey, message, signature } = await request.json();

  // Verify wallet signature (existing logic — KEEP THIS)
  const isValid = nacl.sign.detached.verify(
    new Uint8Array(message),
    bs58.decode(signature),
    bs58.decode(publicKey)
  );
  if (!isValid) return NextResponse.json({ error: "Invalid signature" }, { status: 401 });

  // Sign a Convex JWT
  const privateKeyPem = process.env.JWT_PRIVATE_KEY!.replace(/\\n/g, "\n");
  const privateKey = await importPKCS8(privateKeyPem, "RS256");

  const convexToken = await new SignJWT({ sub: publicKey })
    .setProtectedHeader({ alg: "RS256", kid: "pisp-key-1" })
    .setIssuedAt()
    .setIssuer(process.env.CONVEX_SITE_URL!)
    .setAudience("profit-is-profit")
    .setExpirationTime("7d")          // match 7-day session TTL decision
    .sign(privateKey);

  // Set httpOnly cookie with the Convex JWT
  const response = NextResponse.json({ success: true }, { status: 200 });
  response.cookies.set("pisp-auth", convexToken, {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "lax",
    maxAge: 7 * 24 * 60 * 60,
    path: "/",
  });
  return response;
}
```

**Step 5 — ConvexProviderWithAuth in layout:**
```typescript
// src/app/ConvexClientProvider.tsx
// Source: https://docs.convex.dev/auth/advanced/custom-auth
"use client";
import { ConvexReactClient } from "convex/react";
import { ConvexProviderWithAuth } from "convex/react";
import { useCallback, useMemo, useState } from "react";

const convex = new ConvexReactClient(process.env.NEXT_PUBLIC_CONVEX_URL!);

function useAuth() {
  // Token is stored in cookie — fetch it via a server route
  // or store in React state after login
  const [token, setToken] = useState<string | null>(null);

  const fetchAccessToken = useCallback(
    async ({ forceRefreshToken }: { forceRefreshToken: boolean }) => {
      // If 7d JWT not expired, return from state; else force re-auth
      return token;
    },
    [token]
  );

  return useMemo(() => ({
    isLoading: false,
    isAuthenticated: token !== null,
    fetchAccessToken,
  }), [token, fetchAccessToken]);
}

export function ConvexClientProvider({ children }: { children: React.ReactNode }) {
  return (
    <ConvexProviderWithAuth client={convex} useAuth={useAuth}>
      {children}
    </ConvexProviderWithAuth>
  );
}
```

**Note on token storage:** Since the JWT is httpOnly (for middleware), the client needs a separate signal for auth state. Recommended: keep `pisp-auth` httpOnly for middleware, AND store the raw JWT in a client-accessible cookie or React context for `fetchAccessToken`. The middleware reads httpOnly; the client reads the non-httpOnly version. Alternatively, expose a `GET /api/auth/token` route that returns the JWT from the httpOnly cookie.

### Pattern 5: Convex Mutation (Write Operations)
**What:** Mutations are transactional DB writes, run atomically.
**When to use:** All writes — wallet create/update, trade save, user state update.

```typescript
// convex/wallets.ts
// Source: https://docs.convex.dev/functions/mutation-functions
import { mutation } from "./_generated/server";
import { v } from "convex/values";

export const createWallets = mutation({
  args: {
    tradingWallet: v.string(),
    vaultWallet: v.string(),
  },
  handler: async (ctx, args) => {
    const identity = await ctx.auth.getUserIdentity();
    if (!identity) throw new Error("Not authenticated");

    const userId = identity.subject; // wallet public key = sub claim

    // Check for existing wallets
    const existing = await ctx.db
      .query("wallets")
      .withIndex("by_user", (q) => q.eq("userId", userId))
      .collect();

    if (existing.length > 0) {
      // Update existing (upsert pattern)
      for (const wallet of existing) {
        const newAddress = wallet.walletType === "trading"
          ? args.tradingWallet
          : args.vaultWallet;
        await ctx.db.patch(wallet._id, { address: newAddress });
      }
    } else {
      // Insert both
      await ctx.db.insert("wallets", {
        userId,
        walletType: "trading",
        address: args.tradingWallet,
        balanceSol: 0,
        balanceUsd: 0,
      });
      await ctx.db.insert("wallets", {
        userId,
        walletType: "vault",
        address: args.vaultWallet,
        balanceSol: 0,
        balanceUsd: 0,
      });
    }
  },
});
```

### Pattern 6: Idempotency Check for Trades
**What:** Before inserting a trade, check if it already exists (same user + tokenMint + positionClosedAt).
**When to use:** In `internalMutation` that saves trades after Helius sync.

```typescript
// convex/trades.ts (internal)
// Source: https://docs.convex.dev/database/reading-data
import { internalMutation } from "./_generated/server";
import { v } from "convex/values";

export const saveSyncedTrades = internalMutation({
  args: {
    userId: v.string(),
    trades: v.array(v.object({ /* ... */ })),
    walletAddress: v.string(),
  },
  handler: async (ctx, args) => {
    for (const trade of args.trades) {
      // Idempotency: skip if already exists
      const existing = await ctx.db
        .query("trades")
        .withIndex("by_user_token", (q) =>
          q.eq("userId", args.userId).eq("tokenMint", trade.tokenMint)
        )
        .filter((q) => q.eq(q.field("positionClosedAt"), trade.positionClosedAt))
        .first();

      if (!existing) {
        await ctx.db.insert("trades", { ...trade, userId: args.userId });
      }
    }
  },
});
```

### Anti-Patterns to Avoid
- **Calling runQuery/runMutation from mutations for shared logic:** Extract shared logic as plain TypeScript helpers instead of using ctx.runQuery inside mutations — this adds unnecessary overhead.
- **Using `.collect()` on large datasets:** Only use `.collect()` on small datasets (<1000). Use `.take(n)` or pagination for trade lists.
- **Using Date.now() in queries:** Queries are deterministic and freeze time — put time-based logic in mutations/actions instead.
- **Making external API calls from mutations:** External calls (Helius, CoinGecko) must be in actions, not mutations.
- **Public internalMutation:** Never expose `internalMutation`/`internalAction` to clients — they're for server-to-server orchestration only.
- **Duplicate type definitions:** Never redefine types from schema. Use `Doc<"wallets">`, `Id<"wallets">` from `convex/_generated/dataModel`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Real-time updates | WebSocket subscriptions, polling, SSE | `useQuery` from `convex/react` | Convex queries auto-subscribe; re-renders happen automatically when data changes |
| Type-safe DB access | Manual type assertions, `as any` | `Doc<"tableName">`, `Id<"tableName">` from `convex/_generated/dataModel` | Auto-generated from schema; zero drift possible |
| JWT signing | Custom HMAC or home-rolled signing | `jose` (`SignJWT`, `importPKCS8`) | Standard library, handles key format edge cases |
| RSA key generation | OpenSSL CLI commands, manual JWKS construction | `jose` (`generateKeyPair`, `exportPKCS8`, `exportJWK`) | One-liner key generation with correct JWK format |
| Optimistic UI updates | Manual state management for pending writes | Convex's built-in optimistic updates via `useMutation` | Convex automatically applies and rolls back optimistic updates |
| Transaction atomicity | Manual rollback logic | Convex mutations (all DB writes in one mutation are atomic) | If mutation throws, zero writes happen — fully transactional |

**Key insight:** The `as any` casts in `trade-service.ts` exist because the manually-maintained `database.ts` types diverged from actual schema. Convex eliminates this permanently — the schema IS the type, generated automatically. There will be no `database.ts` equivalent to maintain.

## Common Pitfalls

### Pitfall 1: Token Accessibility for ConvexProviderWithAuth
**What goes wrong:** The JWT is stored in an httpOnly cookie for middleware security, but `ConvexProviderWithAuth`'s `fetchAccessToken` runs client-side and can't read httpOnly cookies.
**Why it happens:** Security model conflict — httpOnly cookies protect against XSS but are invisible to JavaScript.
**How to avoid:** Use two cookies: `pisp-auth` (httpOnly, for middleware) containing a boolean/session flag, and `pisp-convex-token` (non-httpOnly, accessible to JS) containing the JWT for `fetchAccessToken`. OR: expose a thin `GET /api/auth/token` endpoint that reads the httpOnly cookie server-side and returns the JWT — client calls this on mount to get the token.
**Warning signs:** `useConvexAuth().isAuthenticated` always false, or `No tokens to refresh` errors in console.

### Pitfall 2: Schema Field Name Case (camelCase vs snake_case)
**What goes wrong:** Carrying over snake_case field names from Supabase into Convex schema causes the same type mismatch problem from a different angle.
**Why it happens:** Supabase/SQL convention is snake_case; TypeScript/Convex convention is camelCase. Mixing them means generated types don't match the field names used in TypeScript code.
**How to avoid:** Use camelCase throughout the Convex schema (`balanceSol` not `balance_sol`, `tokenMint` not `token_mint`). Update all references in services and types simultaneously.
**Warning signs:** TypeScript errors accessing fields like `wallet.balance_sol` that don't exist on `Doc<"wallets">`.

### Pitfall 3: Calling External APIs in Mutations
**What goes wrong:** Helius fetch or CoinGecko calls placed inside mutations will throw — mutations don't support `fetch` or external I/O.
**Why it happens:** Mutations are deterministic and transactional — they can only read/write the Convex DB.
**How to avoid:** All external API calls go in **actions**. Actions call `ctx.runMutation(internal.trades.saveSyncedTrades, ...)` to persist results.
**Warning signs:** Runtime error "fetch is not defined" or "Cannot call external service from mutation".

### Pitfall 4: JWT RSA Key Format in Environment Variables
**What goes wrong:** Private key PEM string gets newlines mangled when stored in `.env.local` (backslash-n instead of actual newlines).
**Why it happens:** Environment variable parsers handle multiline strings inconsistently.
**How to avoid:** Store private key as JSON-stringified (double-quote escaped) and `.replace(/\\n/g, "\n")` before `importPKCS8`. Or use Convex dashboard environment variables which handle multiline correctly.
**Warning signs:** `jose` throws "Failed to decode/import private key" at runtime.

### Pitfall 5: Convex ID vs String for Foreign Keys
**What goes wrong:** Using `v.string()` for wallet IDs in trades instead of `v.id("wallets")` — loses referential integrity and type safety.
**Why it happens:** Instinct to use strings for IDs (Supabase used UUID strings). Convex has its own `Id<"tableName">` type.
**How to avoid:** Use `v.id("wallets")` for `tradingWalletId` field in trades. Use `Id<"wallets">` type annotation in TypeScript.
**Warning signs:** TypeScript error when passing a `Doc<"wallets">["_id"]` where `string` is expected — actually this means you accidentally used `v.string()`.

### Pitfall 6: Missing Index for Every Query Pattern
**What goes wrong:** Using `.filter()` on table-scan instead of `.withIndex()` — works on small datasets but Convex warns and performance degrades.
**Why it happens:** Developers carry over SQL habits where the DB optimizer picks indexes implicitly.
**How to avoid:** Every `ctx.db.query()` that filters by a field needs a corresponding `.index()` in the schema. Design indexes during schema design, not after.
**Warning signs:** Convex dashboard shows "No index found" warnings; queries work but are slow.

### Pitfall 7: Tests Break if They Import Convex Modules
**What goes wrong:** If test files import from `convex/_generated/api` or `convex/react`, they'll fail because Convex generated files require a live Convex deployment.
**Why it happens:** Convex's generated API is deployment-aware.
**How to avoid:** The 229 existing tests test pure business logic (calculators, parsers, helpers) with no DB dependency — they don't touch Supabase today, and they shouldn't touch Convex either. No test infrastructure changes needed. Keep convex functions separate from business logic functions.
**Warning signs:** Tests suddenly fail with "Cannot resolve convex/_generated/api".

```typescript
    const existing = await ctx.db
      .query("userState")
      .withIndex("by_user", (q) => q.eq("userId", identity.subject))
      .first();

    if (existing) return existing;

    const id = await ctx.db.insert("userState", {
      userId: identity.subject,
      currentLosingStreak: 0,
    });
    return await ctx.db.get(id);
  },
});
```

## Recommendations for Claude's Discretion Areas

### Auth Integration Pattern
**Recommendation:** Use `customJwt` (not Convex Auth beta library). The wallet signing flow stays in the existing `POST /api/auth/verify` Next.js route. After signature verification with `nacl`, sign a 7-day RS256 JWT using `jose`. Store it as a non-httpOnly cookie `pisp-convex-token` for client access + an httpOnly cookie `pisp-auth` (same JWT) for middleware. The `ConvexProviderWithAuth` hook reads `pisp-convex-token` from `document.cookie`.

**Why not Convex Auth (labs):** Convex Auth is designed for email/OAuth flows; it doesn't expose primitives for raw wallet signature verification. The `customJwt` approach gives full control over the `sub` claim (wallet public key) and works with the existing `nacl`/`bs58` verification code.

### API Routes vs Convex Functions
**Recommendation by route:**

| Current Route | Recommended Replacement | Reason |
|---------------|------------------------|--------|
| `POST /api/auth/verify` | Keep as Next.js API route | Wallet sig verification (nacl) runs here; issues JWT; sets cookies |
| `POST /api/auth/signout` | Keep as Next.js API route | Just clears cookies, no DB needed |
| `POST /api/wallets/create` | Replace with Convex mutation `wallets.createWallets` | Direct DB write; client calls `useMutation` |
| `GET /api/wallets/user` | Replace with Convex query `wallets.getUserWallets` | useQuery gives live updates for free |
| `GET /api/wallets/balances` | Keep as Next.js API route OR move balance fetching to Convex action | Currently calls Helius; could be action OR kept as Next.js route (balances page doesn't need real-time) |
| `POST /api/trades/refresh` | Replace with Convex action `sync.syncWalletTrades` | Action can call Helius + write to Convex in one server function |

### Middleware Implementation
**Recommendation:** Keep the existing cookie-based middleware unchanged. The `pisp-auth` cookie presence check continues to work — just now it contains the Convex JWT instead of a wallet address string. No code changes needed in `src/middleware.ts` beyond possibly validating JWT expiry (optional — browser will re-auth if JWT expires).

### Sync Architecture
**Recommendation:** Convex action for sync. Move `trade-service.ts`'s `syncTrades` function into `convex/sync.ts` as a Convex action with `"use node"` directive (to use helius-client which may use Node.js APIs). The action calls `ctx.runMutation(internal.trades.saveSyncedTrades, ...)` to atomically write all trades. The dashboard calls `useMutation(api.sync.syncWalletTrades)`.

**Important:** Move business logic utilities (`helius-client.ts`, `trade-parser.ts`, `tier-calculator.ts`, `cashout-calculator.ts`) into the Convex functions. These can be imported directly into convex functions since they're pure TypeScript. If they use Node.js APIs, add `"use node"` to the action file.

### Test Infrastructure
**Recommendation:** No test changes needed. The 229 tests cover `cashout-calculator`, `tier-calculator`, `trade-parser`, `helius-helpers`, and utilities — all pure functions with no DB calls. These remain in `src/lib/` and continue working. When the business logic is imported into Convex functions, the test files don't need to follow — they test the source functions directly.

### Convex Schema Design
**Recommendation:** Use camelCase field names (not snake_case). Use `v.id("tableName")` for foreign keys. Add an index for every query pattern upfront — cheaper to add indexes during schema design than to add them later when data is growing.

## Open Questions

1. **Helius client Node.js compatibility in Convex default runtime**
   - What we know: Convex default runtime supports `fetch` natively; most browser-compatible packages work
   - What's unclear: Whether `helius-client.ts` uses any Node.js-specific APIs (fs, crypto, etc.) that would require `"use node"` on the action
   - Recommendation: Add `"use node"` to `convex/sync.ts` preemptively — it only affects startup time and is safer for external API calls

2. **7-day JWT expiry vs Convex token refresh**
   - What we know: Convex clients call `fetchAccessToken({ forceRefreshToken: true })` when the token is near expiry; our tokens are 7-day non-refreshable by design
   - What's unclear: Whether Convex's internal token refresh timer (typically 1h) will aggressively call `fetchAccessToken` with `forceRefreshToken: true` before 7 days
   - Recommendation: In the `fetchAccessToken` handler, check if the JWT is still valid (parse exp claim client-side) and return it if so; only return `null` (trigger re-auth) when truly expired

3. **Cookie strategy for client-accessible JWT**
   - What we know: httpOnly cookies cannot be read by JavaScript; `ConvexProviderWithAuth.fetchAccessToken` runs client-side
   - What's unclear: Whether storing JWT in a non-httpOnly cookie is acceptable given the security profile (Solana wallet app, XSS risk is low if CSP is set)
   - Recommendation: Store JWT in both httpOnly `pisp-auth` (for middleware) and non-httpOnly `pisp-convex-token` (for `fetchAccessToken`). Accept the minor XSS exposure since wallet connection requires user interaction anyway, and rotate sessions on reconnect.
