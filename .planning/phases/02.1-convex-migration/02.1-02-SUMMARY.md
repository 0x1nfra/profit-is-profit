# Phase 02.1 Plan 02: Convex Data Access Layer Summary

**Four typed Convex function files providing wallet, trade, user-state, and goal-settings data access with auth guards, index-only queries, and idempotent sync mutations**

## Accomplishments

- Built the complete typed data access layer that replaces all Supabase calls — four Convex function files producing the generated `api.*` client API
- Implemented `saveSyncedTrades` as an `internalMutation` with idempotency check (by_user_token index + positionClosedAt filter) to prevent duplicate trade inserts on repeated syncs
- Created `createWallets` with upsert pattern (patch existing or insert missing) so re-running setup never duplicates wallet records
- All eight exported functions authenticate via `ctx.auth.getUserIdentity()` before touching the database; all queries use `withIndex()` — zero table scans

## Files Created/Modified

- `convex/wallets.ts` - getUserWallets query, getWalletByAddress query, createWallets mutation (upsert), updateWalletBalance internalMutation
- `convex/trades.ts` - getUserTrades query (capped at 50), saveSyncedTrades internalMutation (idempotent)
- `convex/userState.ts` - getUserState query, getOrCreateUserState mutation (creates default streak=0)
- `convex/goalSettings.ts` - getGoalSettings query, initializeGoalSettings mutation (creates default 400 USD/month goal)

## Decisions Made

- `saveSyncedTrades` and `updateWalletBalance` use `internalMutation` so they cannot be called from the client — only the sync action in Plan 04 can invoke them server-side
- `getUserTrades` defaults to 50 records with an optional `limit` argument to allow override without unbounded reads
- `saveSyncedTrades` idempotency uses the `by_user_token` compound index plus a filter on `positionClosedAt` — the same trade (user + token + close time) is never inserted twice
